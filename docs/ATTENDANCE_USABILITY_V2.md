# 出勤与计薪设置易用性优化 · 第二版方向稿

本稿依据用户反馈群截图、当前源代码及受控复现形成，记录第二版的业务约束与设置流程。2026-09-14 已在独立功能分支开发；本次实现与验证见 `USABILITY_V2_ACCEPTANCE.md`。

## 1. 目标与边界

目标：在功能完整、计算规则正确的前提下，减少用户需要理解的参数、规则优先级、跨页面操作和重复确认。

取舍顺序：计算与数据正确 > 变更范围可理解、可恢复 > 常见任务少决策 > 页面简短。少几个控件不能抵消错误计算或隐蔽副作用。

本轮聚焦工资配置、常规出勤、特殊出勤、规则冲突与记录纠错。沿用首页布局、主要功能入口和现有产品风格。共享计算结果的修复会同步到首页、账本、心愿和组件，但不以重排这些页面来解决设置问题。

保留固定/弹性工作记录、固定周/大小周、手动/每周/循环排班、跨日与长班、多段休息、个人假期、工资扣除、生活成本、工资倍率与固定金额、工作阶段、补记和预约等既有能力。

## 3. 首先明确计算的含义

### 3.1 固定月薪与时间单价

用户选择固定月薪时，在整月在职、没有额外工资调整且按约定出勤的前提下，应以填写的月工资作为基本工资目标。日薪和时薪是该目标在相应规则下的折算结果。

月平均天数得到的固定时间单价，与按实际出勤日期累计得到固定月薪，不能默认视为同一件事。固定月薪、固定时间单价、每月不同工时下仍严格按“时长 × 单价”累计，这三项通常不能同时成立。

设计处理：

- 基础设置先确定工资按什么方式支付；月薪/年薪、按天、按小时、按班保留各自语义。
- 固定月薪的计算正确性以月工资基准及明确调整为依据；时间折算不能无提示地改变该基准。
- 固定时间单价估算能力仍保留在相关计算细则中，明确其用途；它与账本结算如何关联，须在计算规格中写清，不能再共用一个含义模糊的参数。
- 工资扣除、生活成本、加班及临时收入继续按各自口径参与计算，预览区分基本工资与收支结余。
- 正确的安排变化可能使参考时薪变化。解释具体原因，不能通过冻结错误数据来保持表面稳定。

这是需要业务计算规格支撑的调整，不能只把旧选项改名为“固定月薪”。旧数据继续保留原口径；不能在升级时静默切换所有用户的历史算法。

### 3.2 出勤与实际记录

分别维护“本来安排怎样上班”“实际上了多久”“这次工资怎样调整”。有薪休息可以有工资而没有工作时长；月薪用户少工作一小时，也不一定按时薪扣一小时工资。

固定周、两周轮换、循环与手动排班是常规安排的不同表达；弹性开始/暂停/结束是实际时间记录方式，可以与常规安排组合。用户无需在一排互斥的混合模式中选择自己的身份。

一份工作在同一日期只有一份生效的常规安排。内部可以保留多个历史版本，界面只呈现当前生效结果和明确的变更入口。

### 3.3 历史与纠错

“从某天开始有新工资/新作息”与“以前填错了，现在修正”是不同操作。前者保留生效日前配置，后者按用户选择的历史范围重算。

保存配置不删除真实计时、手工账目或成就记录。用户主动修正错误后，受影响的派生金额与进度应一致重算，不能承诺所有累计数字永远不变。

## 4. 用户任务与最少必要输入

| 用户要做的事 | 基础流程 | 条件出现的内容 |
| --- | --- | --- |
| 第一次设置这份工作 | 填工资与支付周期 → 确认常规安排 → 核对结果与生效日期 | 按班才设置班次金额；选择轮班才出现循环；固定周不出现排班编辑器 |
| 工资上涨或下降 | 修改金额 → 选择生效日期 → 保存 | 涉及过去时展示受影响日期与历史金额；同一工作调薪不用补录一份工作经历 |
| 设置大小周 | 展示连续两周，分别确认哪些天上班 → 选择从哪周开始 | 摘要始终包含真实星期与日期；“大/小周”可作为辅助名称 |
| 从固定作息改成轮班 | 选择生效日期 → 设置班次及重复方式 → 核对相应工资与工时 | 保留原薪酬规则；需要改变计薪依据时明确展示该变化，而非隐藏在排班启用动作中 |
| 请半天假 | 选择日期与上午/下午 → 确认工资照常或如何扣减 → 保存 | 特殊比例或固定金额仅在用户需要时出现；说明作用于请假半日还是整日 |
| 放长假或假期临时值班 | 选择日期范围或当天班次 → 展示现有假期工资 → 确认是否另加补贴 | 不要求用户手工拼出假期、值班、工资覆盖的优先级 |
| 周末加班按次给钱 | 在加班中选“本次固定金额” → 填金额与时间 | 展示是否另有同时间段加班收入，防止重复计入 |
| 忘记停表 | 打开原记录 → 修改实际结束时间 → 看修正结果 → 保存 | 跨日、重叠、已有账目等冲突在对应字段反馈；无需先删除记录 |

年薪、非周一开始的工作周、不固定工作日及复杂排班继续可达；普通模板之外使用现有自定义能力。不能用表面统一的选项改变旧规则实际含义。

## 5. 信息出现的条件

### 基础设置

进入设置先显示这份工作的已保存摘要：工资支付方式、当前安排、生效日期。点选对应内容编辑。概要必须包含已经生效的特殊规则，防止隐藏后无法察觉，例如“正在使用排班”“本月有一段带薪假期”。

工资与出勤设置保留各自入口，通过当前工作上下文关联；避免同一数值在两个表单中独立保存。

### 特殊出勤

沿用现有日历入口。用户先选日期和“今天发生了什么”，然后只填写与这件事相关的内容。请假类型不得擅自推断用户单位的工资政策；已由用户确认的规则可以作为当前工作的候选默认，并在使用时明确展示。

### 计算细则

折算天数、标准月工时、补贴和特殊计薪保留次级入口，但入口使用明确任务与当前结果。例如“时薪折算：按本月安排”，而不是一个无法判断内容的“高级设置”总开关。

不新增“简洁/专业”版本切换或功能管理开关，让系统根据现有场景展示相关字段。也不通过一层又一层折叠掩盖互相冲突的规则。

### 保存与冲突

普通低影响编辑在当前表单保存，不额外添加固定的确认步骤。只有涉及历史、计算口径变化、工资覆盖或重复计入时，显示相应影响并要求用户明确处理。

预览先回答三个问题：影响哪些日期、改变工资还是只改变工时、历史累计是否会重算。无冲突时不展示全套优先级说明。

例如某天已指定最终工资，再修改出勤：显示“这天已指定基本工资 ¥…，修改出勤时间不会改变该金额”，并提供原工资调整入口。半天固定工资与整日最终工资不能用同一个不带范围的“固定金额”名称。

## 6. 系统承担的复杂度

- 按日期解析所属工作、薪资版本、常规安排与特殊调整，生成一致的有效配置。
- 工作安排、实际时长、基本工资、额外加班分别返回计算来源；不把所有字段硬套入一条全局优先级。
- 同一项当天工资调整通过不同入口访问时，复用同一份业务数据；旧的出勤覆盖、排班最终工资和账本调整需要先建立兼容映射，不能直接删掉其中一类。
- 展示层与保存逻辑共用计算结果，预览与落账使用同一口径；跨日班次明确开班日和实际跨越日期。
- 撤销只恢复本次变更涉及的配置，不粗暴恢复整份本地存储、抹掉之后新增的计时或账目；有后续依赖或并发编辑时明确指出，不能假报撤销成功。
- 历史数据迁移先验证金额、时间与关联记录，提供恢复途径；没有可靠计划工时时显示原因及补充入口，不把“无法折算”伪装为历史成果归零。

## 7. 验收基线

下表是下一版的目标，不表示当前都已满足。正式实施前为每类保留现状样本与预期结果；修复旧行为时明确记录差异原因。

| 场景 | 正确性要求 | 易用性要求 |
| --- | --- | --- |
| 固定月薪，整月正常出勤 | 基本工资符合明确的月薪口径；平均估算与月薪结算不混用 | 不需要试填 21.75、22、23 才知道哪种算法适合自己 |
| 同一份工作中途调薪 | 生效前使用旧工资，生效后使用新工资；月中分摊规则有明确规格 | 在调薪入口完成，不借用换工作功能绕行 |
| 大小周与节假日、补班叠加 | 上班日期与计薪日期各自正确；计薪日期不被当成实际工作时长 | 核对具体日历即可，不要求记住单位与产品术语差异 |
| 固定作息切换手动排班 | 生效日前历史保持；当前及未来依明确规则变化；已保存事实保留 | 保存前能看见日期、工资口径与关联进度的影响 |
| 半天无薪/带薪/比例/固定金额请假 | 未请假的半天保留；调整范围无歧义且不重复扣减 | 不需要自行换算半日倍率或拼公式 |
| 带薪长假期间值班 | 工资、实际工时与额外补贴分别计算，不重复发基本工资 | 记录值班时可看见正在沿用的假期工资 |
| 跨日长班及跨月 | 沿用明确的开班归属与工时拆分，不重复计薪 | 从续班日期也能找到正确的原班次 |
| 忘记结束摸鱼/加班 | 修正重叠校验、关联收入与累计逻辑一致；遵守现有永久成就规则 | 原记录可编辑，不需要删除重建 |
| 旧用户升级 | 原配置、账目、记录与关联不丢失；规则迁移不能静默变更历史 | 正常使用不重新完成一套设置流程 |

易用性测试用同一组任务比较现版与原型，记录无协助完成情况、错误选择、返回修改次数及用户能否解释保存的影响范围。先测固定月薪、大小周、轮班与假期值班用户，不预设单一模板适合所有人。不以页面长度或控件总数作为主要成效指标。

## 8. 实施顺序

1. 复现反馈并建立金额与历史基线。月薪折算和历史调薪已完成受控复现；排班后进度变化继续检查数据与迁移，不能用新文案掩盖计算异常。
2. 完成工资生效范围、出勤/工时/工资调整关系的计算规格；明确哪些是界面调整，哪些是旧算法行为修复，哪些需要数据版本支持。
3. 以本稿八个任务制作设置与变更原型，验证普通和复杂场景都能完成；先收敛重复规则和操作，再减少字段曝光。
4. 分批实现并验证共享计算、旧数据、移动端弹窗及 Android 组件的一致性。
5. 继续使用独立 feature 分支、测试站点与独立 Android 应用 ID。用户验收前不合并 main、不触发正式站点和正式安装包发布。

首轮被撤销的首页/导航改版不沿用。验收前仅发布到独立测试环境。
