# 心愿按顺序分配 · 测试说明

本次继续在 `codex/feature-usability` 开发，只更新独立测试站点和 Android 测试应用。首页沿用原结构，仅现有心愿卡片的数据与状态文字接入共享分配。

交付应用名为 **MoneyDance 心愿测试**，应用 ID `com.cshouuu.moneydance.usability.wishes`，与正式版和之前的易用性 V2 测试版并存。此前临时调试签名无法用于覆盖安装旧包，因此启用新的独立测试身份；原测试应用及数据无需卸载。此后构建从专用 GitHub Actions secret 恢复固定测试签名，支持该心愿测试应用后续更新。测试私钥不入库、不使用正式签名，正式发布流程保持原样。

## 用户可见规则

- 新用户按创建顺序排队，新增心愿放队尾。通过“优先攒这个”把目标移到前面，无需设置优先级数字或百分比。
- 同一份工作收入只累计一次。优先补足当前可参与的目标，溢出自动用于下一目标；全部攒够后的剩余收入保留在待分配余额中。
- 调整顺序只改变操作时刻之后的分配。此前每个目标的分配保留。进度与预计达成时间均考虑完整队列。
- 参与日期在未来的目标暂时跳过，到日期后可以使用待分配余额。只有未来目标时，不累计首个参与日期之前的收入。后续新增或提前参与日期从操作时刻生效，不重新抢占原有目标的历史分配。
- 删除未买目标，释放其已分配金额。降低价格时只释放超出新价格的金额；提高价格保留已有分配并继续补足。
- 标记已买会记录一次购买支出，并从心愿分配中扣除购买金额。提前购买产生的不足单独显示，后续收入先补齐缺口。已经花掉的金额不会因目标退出队列重新分给其他目标。
- 当最后一个目标被删除，已经开始的收入估算继续保留，待分配余额可用于以后新增的心愿。

## 收入口径与旧数据

心愿继续沿用原来的“工资 × 计薪工作时段”估算口径，遵循已保存的工作记录、休息、出勤与工资版本。它不是银行存款余额，也不是整个账本的收支结余；不会把摸鱼收益再次叠加为另一笔工资。仅心愿的已买金额从共享估算收入中扣除，账本其他手工收支不参与此次分配。

旧用户首次看到分配预览：展示统一收入、历史已买金额及每个心愿的旧/新进度。确认后才切换；取消不写入分配计划，也不妨碍原有添加、编辑、删除和购买操作。迁移按创建顺序分配，以前的已买记录按购买时刻扣除，不把各个旧进度直接相加。

计划保存原始心愿与每次调整的时间记录，按时间顺序计算。调序本身不重分历史；工资或出勤纠错时，会用修正后的收入按当时的队列重新计算，避免冻结错误收入。已买金额以心愿购买时记录的价格扣除；本轮未引入与整个账本实时联动的储蓄账户。

## 一致性与恢复

- 心愿页、首页原有卡片与 Android 心愿组件使用共享分配结果。
- 组件即使只选择了后面的某个心愿，仍先考虑完整清单。离开应用后的刷新使用已经按目标分配的未来时段，不把同一份新增收入加给每个组件槽位。
- 组件保留既有未来预测范围和弹性计时边界，快照到期后提示打开应用刷新。
- 编辑、调序、删除及购买在写入前检查数据是否已被其他页面修改。心愿计划、兼容列表、购买账目一起保存；失败回滚，不生成重复购买支出。

## 验收用例

1. 三个同日起始心愿，价格分别 500 / 1000 / 1500 元，收入 600 元：分配应为 500 / 100 / 0，总和 600。
2. 甲已有 100 元，改为优先乙：甲保留 100；之后收入先给乙。刷新应用结果不变。
3. 删除未买的甲：甲的分配释放给后续目标；标记甲已买则不释放已消费金额。
4. 未攒够就标记已买：提示缺口，后续收入先补齐，账本只产生一笔支出。
5. 旧心愿先预览再取消，原记录和模式不变；确认后检查去重后的总额和历史已买扣除。
6. 未来参与、降价、涨价、午休、周末、提前结束工作和历史工资纠错下，金额与预计完成时间仍一致。
7. 安卓组件只展示队列后面的心愿，检查它仍等待前面的目标；对比应用内同一时刻的金额。

自动回归见 `apps/web/src/lib/wishAllocation.test.ts`；原生金额检查见 `apps/web/native/android/tests/WishProgressProjectionTest.java`。真实设备安装与桌面组件展示仍需验收。
